W-2 files for AccuWage Online

Eighteen EFW2 wage files, built by the repo's own writer, that you upload to AccuWage in BSO. You do this to see whether SSA's tester agrees with our W-2 output before a real client file goes out. Eight files should pass clean. Ten are broken on purpose, so you can check that AccuWage catches each defect.

Two-sentence version

Upload reports/accuwage-ty2025/ today, and reports/accuwage-ty2026/ once AccuWage accepts tax year 2026 (likely December). Files 01-08 should come back with no errors. Each of files 90-99 should come back with the one error its manifest row names.

8 / 8clean files pass the independent checker, both years
10 / 10negative files fail only their named rule
36files with every W-2 box recomputed by two models
4open decisions for you

How to run it in AccuWage

  1. Regenerate with your real values stamped into the RA record. Without them the files carry placeholders: submitter EIN 123456789 and BSO User ID PYRAMOS1.
    # from the repo root cd mef-spring-boot-integration ACCUWAGE_SUBMITTER_EIN=<pyramos EIN> ACCUWAGE_BSO_USER_ID=<8-char BSO id> \ ./generate-accuwage-files.sh 2025 # or 2026
    The script writes the files, writes MANIFEST.tsv, and runs the independent checker over the clean files. It should print OK eight times.
  2. Log in to Business Services Online and open AccuWage Online. Pick the tax year that matches the folder.
  3. Upload each .txt file one at a time. AccuWage accepts .txt or .zip. Any file name works.
  4. Compare each result with the expected_result column of MANIFEST.tsv. Write down AccuWage's exact message text for files 90-99. SSA does not publish its message wording, so the manifest quotes the Pub 42-007 rule instead.
Why two years

SSA's online error reference lists an "Invalid Tax Year" condition that includes "does not contain the current calendar year". Today is October 2026. A TY2026 file may be refused until January even though BSO opens TY2026 uploads on 8 December. Neither audit could confirm how AccuWage behaves in December. The fields our writer fills sit at the same positions in TY2025 and TY2026, so the TY2025 set tests the same writer today. Only the wage base ($176,100 vs $184,500) and the Social Security tax maximum ($10,918.20 vs $11,439.00) change.

What's inside a wage file (EFW2)

AccuWage finds every value by its byte position, not by a label. If one field runs one byte long, every field after it shifts, and AccuWage reads a name as a dollar amount. That is why file 97 (one 511-byte record) is a critical error that stops testing.

The format is SSA's EFW2, defined in Publication 42-007. Our writer follows four rules:

  • Every record is exactly 512 bytes of uppercase ASCII, ended by CR LF (\r\n).
  • The first two bytes name the record type: RA, RE, RW, RT or RF.
  • Text is left-aligned and padded with spaces. Money is in cents, right-aligned and padded with zeros. There is no decimal point.
  • Positions are 1-based and inclusive. "RA 29" means byte 29 of the RA record.

The RT order does not follow the RW order. Box 12 DD sits last in RW (463-473) but its total sits at RT 295-309, ahead of Box 12 C. A writer that lays out RT totals in RW order puts DD in the wrong place.

Not in our files

The writer emits no RS (state wage), RO (optional employee data) or RU (RO totals) records. EFW2 allows all three. Missing RS is fine, because SSA does not need state data. Missing RO and RU matters for TY2026 Box 12 TP, TT and TA. Open decision 1 below covers it.

What had to change in the writer first

Two defects would have made our own output fail AccuWage, so the files would have tested our bugs instead of the scenarios. Both spec audits, Opus and Grok working separately from the TY2026 publication, found them.

The submitter contact block was blank

Pub 42-007 section 4.5 marks RA 296-346 (submitter address) and 396-437 (contact name and phone) as required. The writer never filled them, so every file the app has ever produced had this gap.

Box 7, Box 12 and Box 13 now reach the file

Before this change the writer could emit only the six core amounts. A 401(k) employee's file therefore showed no Box 12 D and an unchecked Box 13. The 24 money columns now live in one Efw2Amount enum that the writer and validator share. EmployeeWage carries the extra amounts and the retirement-plan flag. The old 14-argument constructor still works, so existing callers did not change.

How it was verified

  • Unit tests. mvn test passes offline, including new tests that pin tips, Box 12, RW 488 and the RA contact positions to literal values. Another test proves every negative file differs from its clean base and that the structural defects fail the Java validator.
  • Independent checker. mef-spring-boot-integration/efw2_check.py was written only from Pub 42-007, without reading the Java code. It reports OK on all eight clean files in both years, and exactly the intended error on each negative file.
  • Box arithmetic, two models. Opus and Grok each recomputed every box in all 36 files from the scenario inputs. Both found zero mismatches.
  • Code review, two models. Neither reviewer found a wrong position or totals drift. Their smaller findings are fixed: the year-specific wage base in scenario 03, a checker run for TY2025, a strict tax-year parse, locale-free dollar text, a guard against null amounts, and realistic withholding in the 250-employee file.
  • Browser verification of this page was skipped. It is a static report.

Open decisions

1. New 2026 tip and overtime codes need RO and RU records

TY2026 adds Box 12 TP (cash tips), TT (qualified overtime) and TA, which live on the optional RO record with an RU total. TP also requires a tipped-occupation code at RW 490-495. The writer has no RO or RU support, so a 2026 client with reported cash tips or qualified overtime would lose those amounts silently. AccuWage cannot see missing data. Scenario 07 uses Box 7 tips only, which is still valid. Building RO/RU is the next feature if Pyramos clients pay tips or overtime. Your call.

2. The service fixture's employer EIN starts with 00

FixtureWageYearSource still uses EIN 003000004, the IRS ATS Orchid employer. SSA rejects the 00 prefix. The AccuWage files use their own valid EINs, so this matters only if someone uploads a file from the fixture source. I left it alone because 941 tests share that EIN.

3. Submitter gained two required fields

The constructor now takes a contact name and phone, and a blank submitter name throws. Every caller in the module is updated. Any code outside the module that builds a Submitter needs the two new arguments.

4. The independent checker is not part of CI

efw2_check.py runs inside generate-accuwage-files.sh but not in mvn test. Running it in CI would catch a wrong column on Box 12 codes that no scenario uses yet. It needs python3 on the runner.
