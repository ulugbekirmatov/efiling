How the 941 / W-2 checker works

You saw a Form 941 card where line 5d said $4,320.00 of wages and $0.00 of tax, and nobody at that company earns anywhere near $200,000. The page could not see the problem because it only adds up what the database says. This is the script that does the math on its own and tells you where the numbers lie.

Two-sentence version

The checker takes the raw paycheck tax rows, works out what every 941 line and W-2 box should be using nothing but the IRS rates, and prints one line for every place the data, the filed forms, or the page say something different.

It shares no code with the page. If the page and the checker agree, you can trust the page. If they disagree, one of them is wrong, and the finding tells you which number to go look at.

01

The problem it solves

The Form 941 & W-2 page adds up columns from the paycheck tax table. Line 5d column 1 is just the sum of every "Additional Medicare taxable wages" value in that table. If the payroll engine wrote a bad value there, the page shows the bad value with a straight face. Nothing in the page knows that Additional Medicare only starts once one person has been paid more than $200,000 in the year.

A check written inside the page would be built on the same sums, so it would make the same mistake. What you wanted is a second set of eyes that starts from the rates and the rules, not from the page.

→
Everything the checker prints uses employee ids and dollar amounts only. No names, no SSNs. You run it on your machine against a DBeaver export, and the file never comes into a Claude session.

One worked example: the $4,320 on line 5d

Employee 3060, third quarter, the company from your screenshot

This person was paid $5,709.00 in Q2 and $12,548.72 in Q3. Their year-to-date Medicare wages after Q3 are $18,257.72. The Additional Medicare rule says: the slice of this quarter's wages that pushed the year-to-date total past $200,000 is taxable at 0.9%. Here nothing pushed past anything.

Medicare wages YTD after Q3 (Y1)$18,257.72

Both findings come from the same bad row, and that is on purpose. One says "these wages should not exist". The other says "even if they did, the tax is wrong". The screenshot analysis made the same two points by hand. Every other number on that screen passes: $24.00 × 6.2% is $1.49, $12,646.76 × 12.4% is $1,568.20, and so on down the card.

The same rule when someone really does cross the line

To make sure the rule is not just "always expect zero", the tests pay one person $20,000.00 a month. The Social Security wage base stops in October and Additional Medicare starts in November. The checker expects exactly that, and flags a run where it is missing.

Worked example · $20,000.00 a month, wage base $184,500.00, threshold $200,000.00
October: YTD goes $180,000 → $200,000SS wages $4,500.00, Additional Medicare $0.00
November: YTD goes $200,000 → $220,000SS wages $0.00, Additional Medicare $20,000.00, tax $180.00
If October was taxed on the full $20,000warning on that check, error on the year ($200,000 > $184,500)
If November shows $0.00 Additional Medicareerror: expected $20,000.00, got $0.00

03

What one run does

Four steps, then one table of rules.

  1. Turn every row into a unit. A unit is either one paycheck (from the new paycheck_tax_lines.sql) or one employee-quarter row (from the page's own w2c_employee_raw.sql). Both get the same fields plus a "how many paychecks am I" count. Everything after this step does not care which one you fed it.
  2. Walk each employee in date order and carry the Medicare year-to-date. Every unit remembers the total before it (Y0) and after it (Y1). The two threshold rules, Social Security stopping at the wage base and Additional Medicare starting at $200,000, only need Y0 and Y1. That is why a quarter row works as well as a paycheck: the before and after totals are the same whether you cross the line in one check or in a quarter.
  3. Add employees up into a company. Four quarters and a year, each with the same money fields. Line 1 counts the people whose pay period covered the 12th of the quarter's last month, the way the form asks.
  4. Run the table. Every rule is one row: an id, what it expects, what it found, how many cents of slack it gets, and the sentence to print. The runner walks the table. Adding a rule is adding a row, not writing new code.

The dotted inputs are optional. Give it filed 941 rows and it compares each line to its own recomputation and checks the form's own arithmetic. Give it W-2 rows and it compares the boxes. Give it both and it also compares the filed 941 to the filed W-2s, which needs no paychecks at all. Add --page and it runs the page's own engine on the same rows and diffs every line and box, 79 values for the screenshot company.

04

What it checks

Slack means how far off a number may be before it counts. Tax lines get one cent per paycheck, because payroll rounds each check and the form rounds the total. Wages and counts get none.

05

An analogy, and where it stops working

It is like checking a restaurant bill by redoing it on a napkin from the menu prices instead of reading the printed total. If the napkin and the bill agree, pay. If they do not, you know which line to argue about. Where this breaks: a bill is one piece of paper. Here there are three layers that can each be wrong on their own, the paychecks, the filed forms, and the page. The checker redoes the napkin once and holds every layer against it, and it also holds the filed 941 against the filed W-2s, which is a comparison no napkin is involved in.
06

The rule in one line, and how to run it

Recompute from rates, never from the thing you are checking, and report every difference with the id of the row that caused it.

# one row per paycheck: run sql/paycheck_tax_lines.sql in DBeaver, export as JSON
node check_941_w2/check_941_w2.js --year 2026 --paychecks ~/Downloads/paycheck_tax_lines.json

# the rows the page uses, plus a diff against the page engine
node check_941_w2/check_941_w2.js --year 2026 --quarters ~/Downloads/w2c_employee_raw.json --page

# filed forms too, machine-readable output
node check_941_w2/check_941_w2.js --year 2026 --paychecks p.json --f941 941.json --w2 w2.json --json

# the 21 hand-computed tests
node check_941_w2/test/run_checker_tests.js

Exit code 0 means no errors. 1 means at least one error finding. 2 means it could not read the input or the year has no wage constants. Warnings never change the exit code.

Below the findings it prints the recomputed 941 card for Q1 to Q4 and the year, and the W-2 column totals, formatted like the page so you can hold the two side by side.

What it does not do yet

Tips are not modeled. Box 12 code A is not added to box 4, and 941 line 5b column 2 is only derived from the tips amount, because the table has no 5b tax column.

A business that closed mid-year is not flagged for the quarters it stopped filing. Only a quarter with wages and no form is an error.

Nothing has run on real data. That is the next step: export 2026 from DBeaver and run it.
