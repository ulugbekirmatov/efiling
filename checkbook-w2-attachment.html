Mailed checks from a prefund wallet, with the W-2 attached

PR #25 open offline: 313 run, 0 failures bank-funded mailed check: pass wallet-funded: blocked on Checkbook feature/checkbook-mailed-prefund → feature/agent-friendly · 2d1882a
TL;DR

We can now create a Checkbook wallet and send a paper check by mail, paid from that wallet, with the W-2 PDF printed inside the envelope. A bank-funded mailed check already goes through in the sandbox.

The wallet-funded one fails with Mailed checks are not enabled for this account. That's a switch on Checkbook's side. Once they flip it, ./mef checkbook-mailed is the whole retest.

Why

Checkbook doesn't have a "business mail" endpoint yet, so we can't simply mail a document without a check. Their interim answer was to send a physical check paid from a prefund wallet, which is a balance held inside the Checkbook account, and attach the PDF to it. The difference from what we had: a wallet has to be created and funded, and the check request points at that wallet.

!
The request shapes come from Checkbook's own API spec. The spec isn't offered as a download, so we pulled it out of the docs site's page bundle (docs.checkbook.io/reference, v3.0.0). The implementation guide attached to their email wasn't available here. Their docs list no prefund page, no wallet funding call, and no mailed-check examples.

What changed, one story per change

1 · Reading back any mailed check crashed our client

A digital check names its recipient by email, so Checkbook returns recipient as text. A mailed check goes to an address, so Checkbook returns an object. Our CheckbookCheck record expected text, so Jackson threw an error on the first mailed check it saw. That broke getCheck, and also listChecks, which lists every check in the account. So the existing ./mef checkbook would have failed as soon as a mailed check existed, even though it never sends one.

2 · A mailed check needs an address, a mail class, and a funding source

A digital check has one recipient string. A mailed check needs a postal address, a delivery service, and an optional debit account. That account is the hook for prefunding. Leave it out and Checkbook debits the default bank. Put a wallet ID there and Checkbook debits the wallet.

Worked example · the two checks ./mef checkbook-mailed sends

attachmentw2-jordan-rivera-2026.pdf, base64
account omitted (bank)201 IN_PROCESS
account = wallet 418692…fcc400 not enabled for this account

The records check Checkbook's limits before anything leaves the app: line_1, city, state and zip are required and length-capped, the name must be 2 to 180 characters, and the attachment must be at most 7 MB, which is Checkbook's per-PDF limit for mailed checks. Both request types now share one amount rule in CheckAmount, with the same error messages as before.

3 · Wallets can be created and listed, but their bank numbers are never stored

An EXTERNAL wallet comes back with real ACH, RTP and wire account and routing numbers, and Checkbook shows them only once. Holding those in a Java record means they can end up in a log line or a toString(). So CheckbookWallet maps only id, name, balance and date, and a test asserts the account number from the response never appears in the record.

The client has no "fund this wallet" method because Checkbook's API has no such call. Their docs say an INTERNAL wallet is funded by ACH debit or a wallet-to-wallet transfer, and an EXTERNAL one by an ACH, wire, RTP or FedNow deposit to its numbers.

Built on PR #24: a digital check with the W-2 attached

The attachment record and the request style come from the earlier digital-check work, which is merged. Three things learned there still hold for mailed checks:

Send the body as bytes. Checkbook rejects a chunked body ("Fields must be in JSON body"), so every request is serialized to byte[] first and carries a Content-Length. sendPhysicalCheck and createWallet use the same toJsonBytes.
The attachment shape is shared. Both digital and mailed checks take {filename, content}, with the content as base64. CheckAttachment is reused unchanged.
The stored file isn't ready right away, and it comes back changed. On a digital check, the attachment download returns 404 for a few seconds, and Checkbook stamps the check number on every page. The mailed-check test doesn't read the attachment back yet. That's listed under open decisions below.

Open decisions

Weakest part · your call
No guardrails on a funded wallet yet

The 2026-11-06 review found that sends have no HTTP timeouts and no amount cap. With an empty sandbox wallet that costs nothing. With a funded production wallet, a hung request or a mistyped amount spends real money. We should close both before a production key exists.

Smaller
Read back the mailed attachment

Test A checks the id, the amount and the address, but not the stored PDF. Adding the same poll-and-compare the digital test uses would prove the W-2 made it onto the mailed check too. It costs one more live call per run.
