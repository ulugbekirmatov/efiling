Formal verification, bro

Your tests check the cases you thought of. Formal verification checks every case inside a box you draw. Here's what that means, using the duplicate-filing bug we just found in FilingDesk.file.

01

The problem: two clicks, one quarter

Picture this. An operator files Orchid Incorporated's Q3 Form 941. They spot a typo, fix it, and hit send again 200 ms later. Two POST /api/mef/filings requests are now running at the same time, with slightly different bytes for the same client-quarter.

The code has a guard for this. The tests say it works.

guardDuplicatePeriod asks the journal "has this EIN already filed a 941 for this quarter?" If yes, it refuses with NEWSEND_PERIOD_ALREADY_FILED. NewSendDuplicatePeriodTest proves it: file once, file again, and the second one is blocked.

But that test runs the two requests one after the other. Real HTTP requests run side by side. Their steps can mix together in any order, and the test only ever tries one of those orders.

Worked example · Orchid 941, Q3, two bodies (b1 and b2)
Request Abody b1, allowDuplicatePeriod=false
Request Bbody b2 (typo fixed), same EIN, form, period
Orders the unit test tries1 (A finishes, then B) → B blocked ✓
Orders TLC tries (whole model)every one: 6.0 million states
What TLC foundA and B both pass the guard → IRS holds 2 returns for one quarter

The guard and reserve each take a lock, but separately. Between A's check and A's reserve there's a gap, and B slips into it. A test would need to hit that gap by luck. A model checker hits it on purpose, because it tries every gap.

03

How it actually works

You don't run the Java. You write a small model of it: the states it can be in, and the steps that move it. Each step must match one indivisible thing in the code, like one call under one lock. Then you write the promises as invariants and let the model checker grind.

You write

FilingDesk.tla: about 300 lines. Each step names the Java it copies, like Reserve ↔ FileJournal.reserve.

You bound it

2 threads, 4 requests, 1 crash, every SendSubmissions reply. A bound keeps the state count finite.

TLC returns

PASS, or the shortest counterexample: the exact step-by-step path to the broken state.

04

The analogy (and where it breaks)

Testing is test-driving a car down five roads you picked. Model checking is getting the map of every road in town within 10 km and checking that none of them ends at the cliff. Where this breaks: you draw the map yourself, from the code. If the map leaves out a road the Java can actually take, TLC happily says "no cliff" and is wrong. That's why the model has to be able to fail (next section), and why the skill records which commit the map was drawn from.

07

The rule, in plain words

  1. Write the promise in one sentence: "the IRS never holds two unrejected 941s for one quarter."
  2. Write the steps the code can take. One lock, or one call with no shared state, is one step.
  3. Let the checker try every order within a bound.
  4. A fail is a bug only if every step in the trace is something the Java can really do.
  5. A pass covers the model and the bound, not the whole universe. Assumptions stay written down (e.g. "a SOAP fault means the IRS filed nothing").

08

Words, unpacked

TLA+
A language for writing models of systems as states and steps. It's math-flavored, but you only use a small part of it.
TLC
The model checker for TLA+. It explores every reachable state of the model and checks the invariants in each one.
interleaving
One specific order in which the steps of concurrent requests mix together. Two requests of two steps each give 6 interleavings.
invariant
A promise that must hold in every state, such as OneLiveReturnPerPeriod.
counterexample
The shortest path of steps from the start to a state that breaks an invariant: a bug report with the repro built in.
bound
The size limit you set: 2 threads, 4 requests, 1 crash. A pass means "no bug at this size or below".
mutant
A deliberately broken variant. If the check still passes on it, the check isn't guarding that code.
sync commit
The commit at which someone last confirmed the model matches the Java. Covered files changing after it means "re-read the model".
09

The two-sentence version

TL;DR, bro

Tests check the orders you thought of. A model checker tries every order of every step within a bound, which is how it caught two requests both slipping past guardDuplicatePeriod and sending two 941s for one quarter.
