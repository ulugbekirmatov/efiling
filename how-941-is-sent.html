The two-sentence version

We wrap the client's 941 numbers in a header that names Pyramos as the Reporting Agent, put that Return and a manifest in a ZIP, and send the ZIP as an attachment to one certificate-authenticated SOAP call. The IRS answers with a deposit ID right away, which proves only that the ZIP arrived; whether the 941 is accepted comes later in an acknowledgment that we fetch by submission ID.

01

The problem

Orchid Incorporated paid 3 employees $1,000 in Q1 2026. It owes the IRS a Form 941 for that quarter. Orchid doesn't file it. Pyramos Software LLC does, as Orchid's Reporting Agent: a company the IRS lets sign and file employment tax returns for other companies, once each client signs a Form 8655 authorization.

The IRS takes no PDFs and no web form here. To file, five things must all be true at once, and each one has its own reject code when it's wrong:

03

The parcel picture

Think of sending a signed contract by courier. The contract is the 941 Return. The address label is the manifest. Both go into a sealed parcel (the ZIP). The courier's delivery slip (the SOAP message) lists only the parcel's tracking number and postmark, and you must show your badge (the certificate login) before the courier takes anything. The courier hands you a receipt on the spot (the deposit ID). Where this breaks: a courier receipt usually means "delivered, done." Here it means only "the parcel is at the IRS." The IRS opens it minutes later and may still reject the contents, and that verdict comes as a separate letter (the ack) you must go and fetch. And unlike a courier, you can't safely "send it again to be sure": a second parcel is a second federal filing.

The 12 stations

Each card starts with the problem the station solves, then one worked example with real values, then the code that does it. The live entry point is the test ReportingAgentAtsScenarioTest, run by ./run-ra-ats-test.sh 1. It calls stations 1 → 12 in order.

Station 1 · Compose
Orchid's numbers arrive as a "body", never as a full return

Pyramos will file for many companies. If each company's file carried its own header, a client file could claim to be the originator, carry the wrong PIN, or say OnlineFiler. So the client file holds only what belongs to the client: the Filer block (EIN, name, name control, address), the tax period, and ReturnData with the form. Pyramos's code writes the header later.

The body lives at test-scenarios/ats-ty2026/scenario-1-orchid-941/client-return-body.xml. Every value is traced to a PDF line in line-mapping.tsv next to it. Loading it checks four things:

  • The root must be ClientReturnBody. A complete <Return> is refused, which keeps the old OneWell OnlineFiler file out of this path.
  • returnVersion is locked to 2026Q1v4.0, the schema version the IRS publishes for the quarter.
  • quarterEndingDt month must be 03, 06, 09 or 12 and equal the tax-period end month.
  • ReturnData must open with IRS941 (for 941) or IRS941X (for 941X).

Station 2 · Compose
Pyramos must prove it may file as a Reporting Agent before anything is built

Two IRS rejects in September came from Pyramos's own settings, not from Orchid's numbers. The code now refuses both before a single byte is built. ReportingAgentOriginatorFactory.fromEnvironment() reads MEF_EFIN, MEF_RA_PIN, MEF_SOFTWARE_ID, MEF_RA_FILING_IP and the MEF_RA_* name and address from .env. It names the missing variable if one is blank. It also refuses three known-wrong values: OneWell's old EFIN, the stand-in EFIN 000000, and Orchid's EIN used as the agent EIN.

The ReportingAgentOriginator record then checks two IRS rules in its constructor. Value types check the rest: the PIN must be exactly 5 digits, the Software ID exactly 8, the name control 1 to 4 of A-Z 0-9 - &.

Station 3 · Compose
The header is written by code, and no caller can change who the originator is

The ReturnHeader tells the IRS who prepared the return, with which software, from which computer, and who signed it. A caller can't pass OriginatorTypeCd at all. The order of elements is fixed by the IRS schema. One wrong order is a schema reject, so the header is built by one function, top to bottom:

Station 5 · Session
The IRS only talks to a logged-in machine that holds a registered certificate

Anyone can build XML. The IRS has to know the sender is Pyramos's registered system. Login proves it. MefClientService.login() builds a ServiceContext from the ETIN, the ASID, and a test flag (T for ATS, P for production). It then calls the SDK's LoginClient with the PKCS12 keystore that holds the IdenTrust device certificate (O=Pyramos Software LLC).

The SDK signs the login message's MeFHeader and SOAP body with the certificate's private key (RSA-SHA256, rules in mef_config/config/login_client_security_config.xml). The IRS checks the signature against the certificate registered for ASID 10219201 and returns a SAML assertion: a signed token that says "this session is Pyramos". Every later call (SendSubmissions, GetAck) carries that token plus a timestamp instead of a fresh signature (basic_a2a_client_security_config.xml).

Station 6 · Pre-flight
Nothing is sent until the cheap checks pass

An IRS reject takes minutes to come back, and a duplicate filing is a real federal problem. So NewSendSubmissionService.submit runs local checks first, in this order. Each failure here means nothing was sent:

  • Logged in? If not → 401, NewSendNotLoggedInException.
  • EFIN configured and exactly 6 digits, and the XML under the size cap.
  • Idempotency key seen before? The key is a string the caller picks per filing. The ATS test uses ra-ats-scenario-1-orchid-941-<uuid>; HTTP callers send it as the Idempotency-Key header. Same key + same payload + already TRANSMITTED → return the stored receipt, no network call. Same key, different payload → 409.
  • Same quarter already filed? Looks up (EIN, form, period) in the journal. If a CREATED, TRANSMITTED or INDETERMINATE row exists → 409 NEWSEND_PERIOD_ALREADY_FILED, unless the request sets allowDuplicatePeriod=true (the ATS test does, because it re-sends the same test company).
  • XSD validation against the bundled IRS schema schemas/94x/2026Q1v4.0/EmploymentTax/941/Return941.xsd. Mode is enforce in application.yml, so a schema error is a 400.

Station 7 · Pre-flight
The submission ID names the sender and the day it was sent

The IRS needs a name for this one filing that no other filing anywhere has ever used. The format is fixed: exactly 20 characters, [0-9]{13}[a-z0-9]{7}. That is the 6-digit EFIN, then the processing date as year + day-of-year (yyyyDDD), then 7 random lowercase letters or digits.

Station 10 · The wire · point of no return
One SOAP call carries the parcel, and the return is not in the SOAP body

Only one thread may use the IRS session at a time: the IRS limits concurrent sessions and the ServiceContext isn't thread-safe. So transmitReserved first takes a fair lock and waits up to 30 seconds (session-wait-seconds); on timeout it answers 503 and marks the row ABANDONED. Then it calls SendSubmissionsClient.invoke(serviceContext, container), which POSTs to la.alt.www4.irs.gov/a2a/mef/mime/SendSubmissions.

The request is a MIME multipart message. Part 1 is the SOAP envelope. Part 2 is the container ZIP as binary. The SOAP body lists only the submission ID and the postmark. The 941 itself is inside the ZIP.

Station 11 · Afterwards
Three outcomes, not two, because "it failed" is often a lie

If the call times out, the ZIP may already be at the IRS. Calling that "failed" invites a resend, and the resend is a second filing. So the code has no "failed after send" case at all. It sorts every result into one of three outcomes, leaning toward safety:

Station 12 · Afterwards
Acceptance arrives later, as an acknowledgment we fetch by submission ID

After the deposit, the IRS opens the ZIP and runs its business rules: schema, the R-rules, math checks. The verdict is an acknowledgment ("ack"): Accepted or Rejected, with rule codes. The live test calls GetAck with our submission ID every 30 seconds for up to 6 minutes. ACK_NOT_FOUND just means "not yet". Each ack is saved to data/ack-store/<submissionId>.json.

It uses GetAck by ID, not GetNewAcks. GetNewAcks marks every ack it returns as retrieved on the IRS side, so it drains the whole queue, including acks that belong to other filings.

08

Non-obvious behaviors

10

Things most likely to surprise you at 2am

  • Deposit ID ≠ accepted. It only proves the ZIP arrived. Read the ack before telling a client "filed".
  • INDETERMINATE means hands off. Don't resend. Run GetAck on that submission ID first. A resend can create a duplicate federal return.
  • The legacy path is still in the code. SubmissionController / SubmissionService hardcode 941, build the ID inline, and named an SDK class that doesn't exist (SubmissionBinaryAttachment). Use the newsend path only. The legacy path also skips the session lock.
  • GetAck polling can itself retry. RetryConfig retries every exception, including ACK_NOT_FOUND, up to 3 attempts with backoff starting at 5 s, inside each 30 s poll.
  • Never use GetNewAcks to look for one ack. It drains the IRS queue and discards non-matching acks.
  • Schema version is locked per quarter. 2026Q1v4.0 is hardcoded in ClientReturnBody, and FormType points at that bundled XSD folder. A new IRS version needs a code change plus a new schema bundle.
  • Software ID is per tax year. 26996214 is TY2026 only. TY2027 needs a new 2799NNNN ID after ATS.
  • Device IDs and VendorControlNum are derived. They hash "pyramos-ats" + EIN, and EIN + period. That is fine for ATS. Production needs a decision on real device identifiers.
  • RefundDisbursementCd=0 is a trial value that IRS accepted, not one confirmed from an IRS code table. The filing IP is per host, so production needs the real sending host's IP.
  • IRS errors look generic in our logs. The real SOAP fault is only in a2a_sdk.log.* (level FINEST). Search the repo for a reject code before debugging it.

The rule in plain words

The plain-language rule

The client gives us numbers; we add a header that says Pyramos signs as their agent; we write it down; we send it once; and we treat it as filed only when the IRS ack says Accepted. If we don't know what happened, we ask the IRS before doing anything else.

The two-sentence version

A 941 goes out as a ZIP (manifest + Return with a Reporting Agent header) attached to one certificate-authenticated SOAP call, journaled to disk before it leaves and never retried. The deposit ID says it arrived; only the GetAck verdict says it was accepted.
