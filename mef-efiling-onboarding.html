Starting MeF e-filing, end to end

Every step from zero to transmitting live returns to the IRS over Application-to-Application (A2A): the e-Services accounts, the e-file application that issues your EFIN and ETIN, the IdenTrust certificate, Automated Enrollment, ATS testing, and the production cutover — grounded in what already exists in the MeF repo.

TL;DR — the whole process in two sentences

The IRS will not accept a return from software it doesn't know, sent by an entity it hasn't vetted, over a connection it can't authenticate — so onboarding is three approvals in sequence: an e-file application (who you are → EFIN + ETIN), a registered IdenTrust certificate (how you authenticate → Automated Enrollment + ASID), and ATS testing (proof your software works → production ETIN).

The suitability check inside the e-file application is the long pole (up to 45 days); everything else is days, so start the application first and do the certificate and build work while you wait.

The five numbers you'll collect

MeF onboarding is mostly the act of collecting identifiers, each issued by a different step. Learn them once — every later step and every error message refers to them.

IdentifierWhat it isIssued by
EINEmployer Identification Number — your business's tax ID. You need one before anything else; the e-file application is filed under it.IRS (Form SS-4, usually same-day online)
EFINElectronic Filing Identification Number — identifies the originator: who prepared/originated the return. Goes in the return XML and the first 6 digits of every Submission ID.e-file application (phase 2)
ETINElectronic Transmitter Identification Number — identifies the transmitter: the system physically sending returns. Used to log in to MeF. Starts in test status; flips to production only after ATS.e-file application (phase 2)
ASIDApplication System ID — identifies your specific A2A software system. Your certificate is registered against it.Automated Enrollment (phase 4)
CertAn X.509 client certificate from an IRS-approved CA (IdenTrust). MeF A2A has no password login in practice — the certificate is your credential.IdenTrust (phase 3)

EFIN vs ETIN — the pair everyone confuses

One organization can wear two hats: it prepares returns (originator) and it sends them (transmitter). The IRS tracks the hats separately, so a single Form 941 submission uses both numbers in different places. This repo's real values make it concrete:

Login / authentication
ETIN 97661 — the transmitter account opening the A2A session
Manifest <EFIN> field
ETIN 97661 — despite the tag name, the manifest identifies who is transmitting
Submission ID prefix
EFIN 238689 — e.g. 2386892025331test941 (6-digit EFIN + date + suffix)
Return XML OriginatorGrp
EFIN 238689 — who prepared the return
The rule
Transmitter 97661 sends on behalf of originator 238689 — mixing them up is rejected at validation.

The seven phases

In dependency order. Phases 3–5 can run in parallel with phase 2's 45-day wait — that's how you land at 6–10 weeks instead of 4 months.

Week 0
~1–3 days

Phase 1 — e-Services accounts for every key person

Who: each Principal and Responsible Official · Where: irs.gov → “Tax Pros” → e-Services

The IRS won't let an anonymous person file an application that grants filing privileges — so before the company can apply, every Principal (owner/officer) and Responsible Official (the person who will control e-filing day-to-day) must individually prove who they are.

  • Each person creates an IRS online account through ID.me: government photo ID + a selfie/video identity check. Takes minutes when documents are clean; days if it falls to manual review.
  • Use each person's legal name and personal details — mismatches with IRS records stall the e-file application later.
  • Decide now who your Responsible Officials are. Adding one later reopens suitability checks.
Week 0–6
up to 45 days

Phase 2 — IRS e-file application → EFIN + ETIN

Who: Responsible Official · Where: e-Services → “e-file application” · Governing doc: IRS Publication 3112

This is the application to become an Authorized IRS e-file Provider. Submit it first — its suitability check is the longest wait in the whole process, and everything after phase 2 can proceed while it runs.

Fill in the business (legal name, EIN, addresses), list Principals and Responsible Officials, and — the decision that shapes everything downstream — pick your provider options:

RolePick it ifWhat it issues
TransmitterYou will send returns to MeF yourself over A2A. Required for this project.ETIN (test status)
Software DeveloperYou write the software that builds return XML. Pick it if you develop in-house — it gives standing ATS access.ETIN (test-only)
ERO / Reporting AgentYou originate returns (your own, or clients' as a payroll provider filing 94x series).EFIN
Suitability check — what the IRS vets, and the fingerprint rule
  • Everyone listed goes through a tax-compliance check (returns filed, no outstanding IRS debt), a credit check, and a criminal background check.
  • Principals and Responsible Officials without a professional credential (CPA, attorney, Enrolled Agent) must be fingerprinted — done electronically through the IRS-authorized vendor, scheduled from inside the application.
  • The IRS says allow up to 45 days. Clean applications often clear faster; one person's unfiled return stalls the whole company's application.

On approval you receive an acceptance letter with your EFIN, and — because you chose Transmitter — an ETIN. The ETIN is born in test status: it can only talk to the test system until phase 6 is passed.

Phase 3 — Get the IdenTrust IGC certificate

Who: your ops/security owner · Where: identrust.com → IGC certificates for IRS

A2A sessions are authenticated with an X.509 client certificate instead of a password — the IRS trusts only certificates chaining to an approved Certificate Authority, and in practice that means IdenTrust's IGC (IdenTrust Global Common) program. Start this the day you submit the e-file application; identity/organization vetting by IdenTrust takes days to a couple of weeks.

  • Order: on identrust.com, choose the IGC offering for IRS use (they list “IRS – Modernized e-File” as a use case). The product selected for this project: “IGC Standard Medium Assurance | Organization Identity | Device”, purchased in the name of Pyramos Software. Check current pricing and pick the longest validity offered (typically 2 years) — every renewal repeats phase 4's registration.
  • Validation: IdenTrust verifies the organization and the named applicant (documents, sometimes a callback). Only after approval can you retrieve the certificate.
  • Key generation: generate the private key on the machine you control — via the browser pickup flow or OpenSSL. The private key never goes to IdenTrust or the IRS; only the public half travels.
  • Download the chain: you need the IGC Root CA and the issuing SubCA certificate alongside your own, or nothing downstream will trust the chain.

Found in code — the chain is already saved here: Root.txt (IdenTrust Global Common Root CA 1) and SubCA1.txt.

# If you go the OpenSSL route: key + certificate signing request (CSR)
openssl req -new -newkey rsa:2048 -nodes \
  -keyout private-irs.key \
  -out irs-mef.csr \
  -subj "/C=US/O=Your Legal Company Name/CN=mef.yourcompany.com"
# Paste the CSR into IdenTrust's retrieval page; download the issued cert + chain.

Phase 4 — Automated Enrollment: register the system + certificate → ASID

Who: Responsible Official · Where: e-Services → MeF “Automated Enrollment” (AE) application · Governing doc: Automated Enrollment External User Guide

The IRS now knows your company (phase 2) and a CA vouches for your keys (phase 3) — but MeF still has no idea which machine will be calling it. Automated Enrollment closes that gap: it registers your software system as an A2A client and binds your certificate to it.

  • Enroll the system: in the AE application, create an A2A client system under your ETIN. The IRS assigns it an ASID (Application System ID) — this repo's is 23868900.
  • Register the certificate: upload the public certificate from phase 3 against that ASID. At login, MeF matches the cert your client presents to the one on file — an unregistered or expired cert fails authentication before any SOAP call is processed.
  • Assign services: grant the system the transmitter service set — Login/Logout, SendSubmissions, GetSubmissionStatus, GetNewAcks, etc. A service you didn't enable returns an authorization error even with a valid session.
↻

Recurring duty: when the IdenTrust certificate is renewed (phase 3 repeats every ~2 years), the new certificate must be re-registered here before the old one expires — otherwise your transmitter is locked out mid-season with no code change to blame.

Phase 5 — Build the keystore and configure the client

Who: engineering · Where: this repo

The Java SDK wants one file that holds your private key plus the full certificate chain: a PKCS12 keystore. Build the chain file first (your cert, then SubCA, then Root — order matters for some validators), then export:

# 1. Assemble the chain: leaf cert + IdenTrust SubCA + IdenTrust Root
cat your-issued-cert.pem SubCA1.txt Root.txt > irs-cert-chain.pem

# 2. Combine chain + private key into a PKCS12 keystore
openssl pkcs12 -export \
  -in irs-cert-chain.pem \
  -inkey private-irs.key \
  -out irs-mef-test.p12 \
  -name "IRS MEF Test Certificate" \
  -certfile irs-cert-chain.pem

# 3. Verify what's inside
openssl pkcs12 -info -in irs-mef-test.p12 -noout -nodes

Found in code — steps 2–3 are scripted in create-pkcs12.sh and verify-pkcs12.sh at the repo root.

Then wire the identifiers and keystore into the app via environment variables — never hardcoded:

export MEF_ETIN=97661              # transmitter (phase 2)
export MEF_ASID=23868900           # system ID (phase 4)
export MEF_KEYSTORE_PATH=/path/to/irs-mef-test.p12
export MEF_KEYSTORE_PASSWORD='…'
export MEF_KEYSTORE_TYPE=PKCS12
export MEF_KEY_ALIAS='IRS MEF Test Certificate'
export MEF_KEY_PASSWORD='…'

Point mef.sdk.environment in application.yml at ATS — endpoints live in mef_config/ats_endpoints.properties (test: la.alt.www4.irs.gov) and mef_config/prd_endpoints.properties (production).

Phase 6 — ATS: prove the software works this repo is here now

Who: engineering · Where: MeF Assurance Testing System · Governing doc: IRS Publication 4164 + per-form ATS scenarios

Your ETIN can't touch production until your software has demonstrably produced valid returns against the Assurance Testing System (ATS) — the IRS's full test copy of MeF. This is not optional and not a formality: ATS enforces the same schemas and business rules production does.

  • Get the current schema/business-rule packages for your form family and processing year. For the 94x employment-tax series they're versioned per quarter — this repo already tracks them in 94x-2026/ (e.g. 94x_Quarterly_BusinessRules_Schemas_2026Q1v2.0).
  • Run the IRS's published ATS scenarios for each form you intend to file — predefined test returns with known-correct data (repo folder: test-scenarios/). Each must come back Accepted in the acknowledgment.
  • Exercise the full service loop, because the IRS checks that transmitters handle it: Login → SendSubmissions → GetSubmissionStatus → GetNewAcks → Logout.
  • Then call the e-help Desk (866-255-0654): they review your ATS results and flip the ETIN from test to production status. Nothing flips automatically.

Hard-won lessons already paid for in this repo

  • Submission ID format is exactly 20 characters — 13 digits + 7 lowercase alphanumerics, regex [0-9]{13}[a-z0-9]{7}. Discovered via SDK bytecode analysis; wrong format is rejected client-side. (SUBMISSION_ID_FORMAT.md)
  • The manifest is mandatory — EFIN, TIN, and tax-period dates must be present; a null manifest fails serialization. (FORM_941_SUBMISSION_IMPLEMENTATION.md)
  • Reuse the login's ServiceContext for every subsequent call — a fresh context invalidates the SAML session.
  • Use in-memory constructors for SubmissionXML / SubmissionManifest; the file-based paths break SDK serialization.
  • Java 17 needs the --add-opens/--add-exports JVM flags from CLAUDE.md — already baked into pom.xml for mvn spring-boot:run.

Phase 7 — Production cutover and the ongoing duties

Who: engineering + Responsible Official

Once the e-help Desk confirms the ETIN is in production status, the cutover itself is small: switch mef.sdk.environment from ATS to PRD so the SDK reads prd_endpoints.properties, and confirm submissions carry the production test-code (the SDK's TestCdType distinguishes test from live traffic). Send one real return, watch it through status → acknowledgment, and you are e-filing.

Three duties never end:

  • Certificate lifecycle — renew with IdenTrust before expiry and re-register in Automated Enrollment (phase 4's callout). Put the expiry date in a calendar with a 60-day lead.
  • Schema/business-rule updates — the IRS revises them per quarter for 94x forms (see the version churn inside 94x-2026/: v1.0 → v4.0 within a single quarter). Filing against a retired version gets rejections, not warnings.
  • e-file application upkeep — personnel or address changes must be updated in the application; a stale Responsible Official can suspend the EFIN.

Questions that come up every time

Do we really need both an EFIN and an ETIN?
Yes, if you both prepare and transmit. They answer different questions — "who made this return?" (EFIN, in the XML) vs "who is sending it?" (ETIN, at login). A payroll provider transmitting for clients uses its own ETIN with each client's context; this repo transmits under ETIN 97661 for originator EFIN 238689.
Which IdenTrust certificate exactly?
The one this project selected: “IGC Standard Medium Assurance | Organization Identity | Device” — an organization-identity device certificate, right for an unattended transmitter system. Confirm current pricing on identrust.com at purchase time. What never changes: it must chain to the IGC Root the IRS trusts, which is the root already saved in Root.txt.
How long does the whole thing take?
6–10 weeks when phases overlap. The 45-day suitability check dominates; IdenTrust vetting (1–2 weeks) and ATS iteration (days to weeks, depending on how many forms and how clean your XML is) fit inside that window if started immediately.
What does it cost?
The IRS charges nothing for the e-file application, enrollment, or ATS. The IdenTrust certificate is the only purchase — order of a few hundred dollars per validity period — plus the electronic fingerprinting fee for any non-credentialed principals.
Can we skip ATS since the software "already works"?
No. The ETIN is created in test status and only the e-help Desk moves it to production, after reviewing ATS results. Re-testing is also required when you add a new form family later.
What breaks first in year two?
The certificate. It expires before anything else needs touching, and the failure looks like a sudden authentication error with no code change. Renew with IdenTrust, rebuild the PKCS12 (create-pkcs12.sh), and re-register the new cert in Automated Enrollment before the old one lapses.
