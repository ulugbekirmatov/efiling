Registering the MeF application with the IRS

The exact path from where Pyramos stands today — certificate in hand, no EFIN — to transmitting clients' Form 941 returns over A2A as an IRS Reporting Agent. Researched 2026-08-28 against current IRS publications (Pub 3112 Rev. 11-2025, Pub 4163 Rev. 12-2025, Pub 1474 Rev. 4-2026, Pub 5078 Rev. 12-2025, IRM 3.42).

✓ IdenTrust IGC certificate issued ✓ 2026 94x schemas & ATS scenarios downloaded ✓ A2A code proven on ATS (OneWell identifiers) → Next: Form 8655s, then the e-file application Long pole: 45-day suitability check

Three findings that change the plan

Before the step-by-step: three things the research surfaced that are easy to get wrong, each of which would cost weeks or produce IRS rejects.

1 · Reporting Agent alone is not enough — select all three provider options

To transmit its own clients' returns over A2A, Pyramos must check Reporting Agent, Transmitter, and Software Developer on one e-file application. IRM 3.42.4.10.3.1: a Reporting Agent only receives an ETIN if it indicates it will also be a Transmitter. And without Software Developer there is no Software ID — rule R0000-904-03 rejects any return whose SoftwareId hasn't passed testing for the form family and tax year — and no access to the Secure Object Repository, which since Pub 4163 Rev. 12-2025 is the only distribution channel for schemas and business rules.

2 · Form 8655s are a prerequisite, not a follow-up

The e-file application validates that at least one Form 8655 (Reporting Agent Authorization) is already on file in the RAF for Pyramos's EIN when the Reporting Agent option is added (Pub 3112, p. 17). Client authorizations gate the application, which gates everything else — start collecting signed 8655s now.

3 · The repo's EFIN/ETIN model is wrong and will reject

EFIN_ETIN_USAGE.md puts the ETIN in the manifest <EFIN> and the EFIN in OriginatorGrp. Rule R0000-054-01 (Reject and Stop) requires the manifest EFIN to match the OriginatorGrp EFIN, and the schema defines the manifest field as the originator's identifier. For Pyramos: one EFIN in both places; the ETIN is used only for A2A login and the ASID binding. (The OneWell submissions passed on ATS, where EFIN/name-control rules are relaxed — don't carry the pattern to production.)

The seven phases

In dependency order. Phase 0 and phase 1 start immediately and in parallel; phases 3–4 prep work fits inside phase 2's 45-day wait.

0

Client authorizations — Form 8655 + Reporting Agent's List

start now
Who: Pyramos ops/legal, per clientDuration: 2–4 weeks incl. RAF postingGoverning: Rev. Proc. 2012-32 · Pub 1474 (Rev. 4-2026) · Form 8655 (Rev. 1-2024)
  • Each client signs Form 8655 (Rev. January 2024 or later). Line 15 = returns Pyramos may sign and e-file (940/941/943/944/945; authority for a form automatically covers related forms — 941 → 941-X, 941 (sp), vouchers). Line 16 = deposits/payments via EFTPS. Lines 17–18 = disclosure.
  • E-signatures are allowed only under Pub 1474 §01.03's specific methods — generic e-signature guidance for other forms does not apply, and each e-signed 8655 must carry evidence of the signature event.
  • Submit the 8655s with a Reporting Agent's List — clients in ascending EIN order, separate lists for additions and deletions. The IRS returns an add/error list with each employer's Name Control (you'll need those name controls in the return XML).
  • Where: IRS, Accounts Management Service Center, MS 6748 RAF Team, 1973 N. Rulon White Blvd., Ogden, UT 84404 — or fax 855-214-7523 (max 25 forms per transmission).
  • Over 100 client submissions per week the List must go electronically via SLFT B2B (the old SDT channel was fully retired December 2025, and the IRS can't support optional SLFT use below the threshold) — at launch volume, paper/fax is the path.
  • Retain a copy or reproducible image of every original 8655 at the principal place of business until the limitations period of the last return filed under it expires.
1

e-Services accounts (ID.me) for every key person

parallel with 0
Who: every Principal, every Responsible Official, every future MeF System EnrollerWhere: irs.gov/e-services → E-file Provider ServicesDuration: 1–3 days
  • ID.me identity verification is mandatory (government photo ID + selfie/video); Login.gov is not offered for e-Services. Minutes when documents are clean, days if it drops to manual review.
  • All Principals and Responsible Officials must have accounts before the application can be submitted. Pub 4163 recommends at least two Responsible Officials for backup. For an LLC, a Principal is "an individual authorized to act for the entity in legal and/or tax matters." Each must be a US citizen or lawful permanent resident, 18+.
  • Decide the roster now — adding a Principal or Responsible Official later reopens suitability.

The IRS e-file application → EFIN, ETINs, RA PIN, Software ID

Provider options — check all three:

OptionWhy Pyramos needs itYields

  • Fingerprinting: every Principal and Responsible Official without a qualifying credential (attorney, CPA — not Enrolled Agent) is fingerprinted by electronic Livescan through the IRS Authorized Vendor, scheduled per-person from the Application Summary page → Terms of Agreement Signature(s) & Personal Information.   • Delegations to set immediately (needed for phase 4): grant MeF System Enroller to one or more Responsible Officials or Delegated Users, and Add & Change Software Package Information to whoever runs the questionnaire.

Pyramos Software Certificates/your-issued-cert.pem: O=Pyramos Software LLC, CN=c2s.pahealthmanagement.org, issued by IGC Device CA 2 (chain: SubCA1.txt → Root.txt), RSA 2048 / SHA-256, valid 2026-08-21 → 2027-08-21. Diary the renewal for ~July 2027

It's a one-year certificate. Expiry is a hard stop on transmission, and each renewal requires a Replace Certificate action in Automated Enrollment. Note the old OneWell cert has the same CN (c2s.pahealthmanagement.org, O=Onewell LLC) — only the organization differs; don't mix them up when building keystores.

4

Automated Enrollment → ASID + certificate registration

needs phase 2 + cert
Who: the MeF System Enroller (delegated in phase 2)Where: e-Services / Integrated Enterprise Portal → Automated Enrollment (AE)Duration: same day

This is the step that tells MeF which machine will be calling it. You supply:

  • EFIN + a 2-digit sequence number (00–99) → the ASID is the 8-character concatenation.
  • Application system name (≤30 chars) and description (≤50).
  • The ETIN(s) to bind to this system.
  • The A2A services to authorize. Unselected services simply fail at runtime, so over-select: Login/Logout, SendSubmissions, GetSubmissionStatus, GetNewSubmissionsStatus, GetAck, GetNewAcks, GetAcksByMsgID, ETINRetrieval, EtinStatus.
  • Upload the certificate (the public leaf from Pyramos Software Certificates/your-issued-cert.pem).

Status goes new → active automatically. Later lifecycle actions: inactivate/reactivate, Replace Certificate (used at every renewal), un-enroll (permanent — the ASID is gone). Only the e-Help Desk can lift a disabled status. Then rebuild the keystore: chain + key → PKCS12 via create-pkcs12.sh (fix its stale cd path first), verify with verify-pkcs12.sh, and point MEF_KEYSTORE_PATH / MEF_KEY_ALIAS at it in .env.

Confirm: one ASID or two?

Pub 4164 §4.1.6 says a separate ASID must be used for testing digital certificates, but the AE External User Guide (still the 10/2017 revision — expect UI drift) draws no ATS/Production distinction. Ask the e-Help Desk before enrolling.

5

ATS — scenario testing and the A2A communications test

needs Software ID + ASID
Who: dev + opsDuration: 1–3 weeks + daysGoverning: Pub 5078 (Rev. 12-2025, PY2026)

Two distinct tests for two different hats — most write-ups conflate them:

  • (a) Scenario testing, as Software Developer. For 94x Quarterly TY2026: three standard Form 941 scenarios + one 941-X scenario + Scenario 10 (94x On-Line Signature PIN registration). Passing at least one 941 scenario earns "Pass" status for Production. Passing quarterly does not cover the annual forms (940/943/944/945) — those need a separate e-Help Desk arrangement. Notify the e-Help Desk when ready to test. All test filer EINs must begin with 00 (R0000-148) — the repo's Orchid scenario EIN 003000004 already complies. Local material is staged: test-scenarios/941-scenario-1-orchid-q1-2026/ and 94x-2026/.
  • (b) Communications test, as Transmitter/Reporting Agent. A one-time, first-year, error-free transmission test — and since Pyramos will submit through A2A, it must be performed through A2A (IRM 3.42.4.13.2). Not repeated when adding forms later.

PY2026 ATS opened October 14, 2025; communications testing is available any time since. ATS is slower than production and can't be used for load testing.

6

Production cutover

after the comm test
Who: e-Help Desk, 866-255-0654Duration: 1–3 days
  • The Forms Transmission Status on the application starts in Test; the IRS flips it to Production after the communications test passes — nothing flips automatically on your side.
  • Ask for a separate Test-type ETIN on the same call. Once the original ETIN moves to Production you lose your ATS path on it (per the MeF employment-tax FAQ); a standing test ETIN keeps regression testing possible forever. Re-testing on the production ETIN requires flipping it back to Test, which blocks live filing meanwhile.
  • Config switch: mef.sdk.environment: PRD, production ETIN in .env, and import the production MeF server SSL chain. These rotate quarterly (current bundle: maincert-4q26.zip / ATS altcert-4q26.zip, valid Aug 10 – Oct 26, 2026) — a recurring operational task; missing it breaks transmission.
  • Note the PRD endpoint discrepancy already in the repo: application.yml says www.irs.gov, the SDK's prd_endpoints.properties says la.www4.irs.gov — the SDK properties file is what's used; reconcile before cutover.
  • Optional: Pyramos appears on the IRS "TY2026 94x MeF providers" list once ATS is passed.

Then: the code changes the new role requires

The existing Spring Boot integration was built for a self-filer (OneWell, originator type OnlineFiler). Checked against the repo's own 2026 schemas and business rules (94x-2026/…/2026Q1), filing as a Reporting Agent requires, in rough order:

  1. Return header: OriginatorTypeCd → ReportingAgent. Keeping OnlineFiler trips R0000-119-01 (requires an EFIN starting 10/21/32/44/53), and EMPL-003 then requires adding a ReportingAgent94XFilerGrp block (Pyramos's EIN, business name, name control, address) alongside the per-client <Filer>.
  2. Signature: replace OnlineFilerPINGrp with ReportingAgentPINGrp — the 5-digit RA PIN (R0000-187: not all zeros; R0000-188: must match the e-file database), RAPINEnteredByCd = REPORTING AGENT, JuratDisclosureCd = REPORTING AGENT PIN.
  3. Identifier fix: Pyramos's EFIN in both the manifest EFIN and OriginatorGrp (R0000-054-01); manifest TIN = the client's EIN per submission (R0000-079). Rewrite EFIN_ETIN_USAGE.md accordingly.
  4. Real Software ID: replace the placeholder 12345678 in the return XML with the issued 2699NNNN (R0000-904-03).
  5. Multi-tenancy: a client model (EIN, name, name control, address, tax period, 8655 authorization status) and persistence of submission ↔ deposit ID ↔ status ↔ acknowledgment per client — acknowledgment retention is an IRS requirement, and today the app stores nothing.
  6. Session hygiene: implement real logout via LogoutClient (today's logout only clears local state, leaving IRS sessions open) and add expiry/refresh — required at Reporting Agent volume.
  7. Toolkit currency: current IRS WSDLs are R10.9 = A2A Toolkit v16.0 — matching Version_16/ in the repo (the checked-in sdk-reference WSDLs are older, R10.3). The SDK jar must be installed into ~/.m2 before anything builds — see CLAUDE.md and CODE_MAP.md §6. Newer toolkits come from mefmailbox@irs.gov with subject "A2A Toolkit".
  8. Purge OneWell values: ETIN 97661, EFIN 238689, ASID 23868900 hardcoded in test-mef-login.sh, the integration tests, and docs; recreate .env with Pyramos values as each identifier is issued.
