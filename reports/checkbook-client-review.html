Checkbook.io client review

The goal is to know what breaks before the Checkbook sandbox client grows from a $1.00 probe into paying people and attaching their W-2. Eight reviewers from two vendors covered four lenses, two seats per lens. Every finding below was re-checked against the code, and the disputed ones were settled by running code.

Verdict. The sandbox probe is sound. It cannot reach production, the secret key stays masked, the W-2 sample is synthetic, and the offline suite cannot spend money. It is not ready to pay anyone. Three things decide that:

  • A retry can pay twice. Nothing is journaled before the POST, a null or blank Idempotency-Key still sends, and the only caller mints a fresh UUID per attempt.
  • No HTTP timeout exists, so a stalled Checkbook call hangs forever and invites that retry.
  • Any amount of at least one cent is legal, with no ceiling, and it goes on the wire as 1E+2 or 100.000 if that is how the caller built it.

One adjacent defect outranks all of these for today. The .env loader prints MEF_RA_PIN in clear at every boot.

Findings

highA retry after a lost response creates a second check

CheckbookClient.java:41-50 · CheckbookSandboxTest.java:56, 74 · seats: DeepSeek 1, 3, 4 · Grok 1, 3, 4

Say the POST reaches Checkbook, the check is created, and the response is lost. The caller then holds an exception and no check id. The client stores nothing before the send. It offers no lookup by key, so the next attempt cannot know the first one landed. The only demonstrated caller passes UUID.randomUUID() on every attempt, so the retry is a brand-new payment.

The key itself is not guarded. Boot 3.2.0 builds the RestClient on SimpleClientHttpRequestFactory, whose addHeaders turns a null value into "". So sendDigitalCheck(req, null) and sendDigitalCheck(req, "") both POST with an empty Idempotency-Key. The returned check is never compared to the request either. A reused key with a changed amount gets the old check back, and the caller cannot tell.

return http.post()
        .uri("/check/digital")
        .header(IDEMPOTENCY_KEY_HEADER, idempotencyKey)   // no null/blank check, nothing journaled
        .body(toJsonBytes(request))
        .retrieve().body(CheckbookCheck.class);
Verified

javap on spring-boot-3.2.0.jar shows ClientHttpRequestFactories.get trying HttpComponents, Jetty, and OkHttp, then Simple. None of the first three are on the classpath. A probe test against MockRestServiceServer showed the header present with value [null]. Compare FilingDesk.file, which reserves a CREATED row before the IRS call and replays on INDETERMINATE.

highNo connect or read timeout

CheckbookClient.java:30-38 · seats: DeepSeek 1, 3, 4 · Grok 4

The client uses the injected builder as is. src/main sets no request factory and no timeout. Boot's DEFAULTS settings carry null durations, so SimpleClientHttpRequestFactory never calls setReadTimeout, and HttpURLConnection waits forever. A Checkbook endpoint that accepts the connection and never answers parks the calling thread for good. Behind a controller, that is one Tomcat worker per hung payment. It also feeds the finding above, because an operator who kills a hung run and reruns it sends a second check.

Verified

A grep of src/main for timeout and request-factory types found nothing. The factory choice was confirmed with javap as above.

highAdjacent: the .env loader prints the RA PIN at boot

config/DotenvEnvironmentPostProcessor.java:61-68 · seat: DeepSeek 2 · outside the Checkbook package

The loader masks a value only when its key contains PASSWORD or KEY. MEF_RA_PIN, MEF_EFIN, MEF_ETIN, and MEF_ASID match neither, so every ./mef checkbook run and every app start writes them to the console. The Checkbook keys are masked only because their names contain KEY.

String displayValue = key.toUpperCase().contains("PASSWORD") ||
                     key.toUpperCase().contains("KEY")
        ? "***" : stringValue;
System.out.println("  " + key + " = " + displayValue);
Verified

Read in source. The loader is registered in META-INF/spring.factories.

medNo amount ceiling, and the wire token is not canonical

DigitalCheckRequest.java:22-27 · CheckbookClient.java:28 · seats: DeepSeek 3 · Grok 3

The constructor checks a floor of 0.01 and a cent scale on stripTrailingZeros(), then keeps the original value. A plain new ObjectMapper() writes BigDecimal.toString(), so the token on the wire is whatever form the caller built. A payroll bug that passes 1E+20 constructs and posts.

Verified

Run on JDK 17 with Jackson 2.15.3, and through the real client in the probe test (1E+2 appeared in the request body). Checkbook's parser was not tested. A strict parser would reject a payment the constructor allowed. A lenient one pays any magnitude.

medAn empty 2xx after a POST is not a CheckbookException

CheckbookClient.java:43-49 · found by the parent's probe

A 201 with no body made the client throw Spring's UnknownContentTypeException. A caller that catches CheckbookException misses it, and the check may already exist with no id in hand. That is the ambiguous case from the first finding, reached by another path.

medlistChecks returns only the first page

CheckbookClient.java:68-75, 110-112 · seats: DeepSeek 1 · Grok 1, 4

One GET /check with no page parameter, and page, pages, and total are ignored. Any reconciliation such as "did this payment go out?" silently misses checks past page one. The live test's anyMatch holds only while the new check sorts onto page one. Checkbook's default page size was not checked.

medError messages carry Checkbook's field echoes into logs

CheckbookException.java:13 · CheckbookClient.java:92-108 · seats: DeepSeek 2 · Grok 2

The exception message is the error string plus every more_info value, unredacted. If Checkbook echoes a recipient email, an amount, or an employee-named attachment filename, that text lands in any log of the exception. Today only sandbox and example.com values flow, so this is latent.

lowSmaller items

  • ./mef checkbook sends two $1.00 checks per run, one per test method, while the class comment says one (CheckbookSandboxTest.java:51, 66). Seat: Grok 4.
  • recipient accepts any non-blank string, despite the "email or phone" comment. name, description, and attachment size have no cap, though the filename is capped at 128. Seats: DeepSeek 3, Grok 3.
  • getAttachment returns any 200 body as the PDF, with no content-type check. Seat: DeepSeek 1.
  • LiveIrsTestGuardTest scans only for .probe( and .login(. A future test calling sendDigitalCheck without @LiveSandboxTest would run in CI. Seats: DeepSeek 4, Grok 4.
  • The static A2A_TOOLKIT_HOME block in CheckbookSandboxTest is not needed. This test never touches the IRS SDK. Seats: DeepSeek 4, Grok 4.

Checked and clean

  • Clean. Production is unreachable. CheckbookEnvironment has one constant and the client hardcodes it.
  • Clean. The live guard holds. @LiveSandboxTest runs only when -Dmef.live.test=CheckbookSandboxTest, which ./mef check and CI never pass.
  • Clean. CheckbookProperties.toString masks the secret, and no actuator exposes config props.
  • Clean. The W-2 sample is synthetic: EIN 00-0000000, a "(SAMPLE)" employer, SSN last four only.
  • Clean. A byte[] body carries Content-Length. A JSON number for number coerces to a String.
  • Clean. An HTML 502 maps to CheckbookException(502, "unparseable error body"), as the probe showed.

Before this client pays anyone

These are recommendations. Nothing was changed.

  1. Put a pay desk in front of the client, shaped like FilingDesk. Derive the idempotency key from the payment's content, journal it before the POST, and on an unknown outcome reconcile by key instead of resending.
  2. Require a non-blank key in sendDigitalCheck, and check that the returned amount and recipient match the request.
  3. Set connect and read timeouts on the client's own request factory.
  4. Add an amount ceiling, normalize with setScale(2), and write the amount as a plain decimal.
  5. Page through listChecks, and map an empty or unreadable 2xx to CheckbookException.
  6. Separately, mask every .env value in the startup print, or drop the print.
