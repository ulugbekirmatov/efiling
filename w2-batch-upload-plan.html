Implementation plan · MeF

W-2 batch upload

Pyramos has to give Social Security one wage file for tax year 2026. The MeF send cannot carry a W-2. This plan builds that file in the Spring Boot app and leaves the upload to a person on Business Services Online. Decision. Build Phases 1 through 7. The federal file writer comes first. State copies and W-2c stay out, because they are different files and different portals.

TL;DR

The app writes one combined wage file for every client. A person checks it with AccuWage and uploads it on Business Services Online. The app stores the file and the Wage File Identifier. It never logs into Social Security.

Phase 1

A pure 512-byte writer

FormType stays the closed 94x list. A new package, com.irs.mef.wagefile, turns employer and employee rows into bytes. Money is integer cents. The writer does not call SendSubmissions and does not touch MefClientService.

  1. Add types for the submitter, one employer, and one employee wage row.
  2. Add Efw2Writer. It emits RA, then each employer's RE, RW rows, and RT, then RF.
  3. Test one employer and one employee at 250000 cents. Assert five records, 512 bytes each, and a zero-filled wage field.

Phase 2

Reject a file SSA would return

The validator runs on the bytes before anyone uploads. It checks length, order, and totals. It does not call AccuWage.

  1. Fail a record that is not 512 bytes.
  2. Fail an RT whose wage sum disagrees with that employer's RW rows.
  3. Fail an RU with no RO, and an RV with no RS.
Efw2Validator
Phase 3

Keep the exact bytes

A resubmit has to reuse the file SSA already saw. NewSendSubmissionRecord stores a SHA-256 and drops the XML, so this file gets its own directory. Add mef.wagefile.path, default data/wage-files, beside mef.newsend.journal.path.

  1. Each run is a folder with the bytes, the sha256, the tax year, the employer EINs, a status, and a blank Wage File Identifier.
  2. Statuses are BUILT, UPLOADED, RETURNED, and COMPLETE.
  3. A test writes a file and reads the same bytes back. The NewSend journal is not written.

Phase 4

Build from a fixture first

Payroll rows live in the sibling database, not in this repo. onepay_employee_tax_payment has tax_amount and taxable_wages keyed by tax_type_id, and the DDL ships no seed ids. hr_employee stores social_security_last_five_number only. The first loader reads a checked-in fixture. The live query waits until those codes are named.

  1. Add WageYearSource for one tax year of employers and employees.
  2. Add FixtureWageYearSource with the corrected Orchid quarter, wages 2500.00.
  3. Do not add a C2S query in this phase.

Phase 5

Match the file to the 941 quarters

For each quarter, compare the wage file with Form 941 line 2 WagesAmt, line 3 FederalIncomeTaxWithheldAmt, line 5a column 1 SocialSecurityTaxCashWagesAmt, and line 5c column 1 TaxableMedicareWagesTipsAmt. A 941-X replaces that quarter with column 1. Column 4 is tax. On Orchid Q1 the file must show 2500.00, not the original 1000.00 and not the 186.00 tax. The check takes those amounts as input. It does not read the journal hash.

  1. Fail the file when wages are 1000.00 and the corrected quarter is 2500.00.
  2. Pass the file when wages are 2500.00, withholding 250.00, Social Security wages 2500.00, and Medicare wages 2500.00.

Phase 6

Build the file, then record the upload

One call writes the year file and returns the path and the hash. A second call stores the Wage File Identifier a person copied from the Business Services Online receipt. There is no browser automation and no MeF login.

  1. Add POST /api/mef/wage-files to build the year file.
  2. Add POST /api/mef/wage-files/{id}/receipt to store the identifier and set status UPLOADED.
  3. Tests call the services. They do not open a socket to SSA.
context path /api
Phase 7

Resubmit a returned file from the saved bytes

Publication 42-007 puts the resubmit flag in RA position 29 and the prior Wage File Identifier in positions 30-35. The resubmit reads the saved bytes, sets those fields, and writes a new run that points at the original. It does not rebuild totals from payroll. A completed file with wrong data is a different publication and is not this phase.

  1. A test sets RA position 29 to 1 and positions 30-35 to a known identifier.
  2. The original bytes stay on disk.
